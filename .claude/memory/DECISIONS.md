# Decisions
- 2026-10-25: Order status flow (script 0019, decided by Claude because she said "whatever you decided is right"): PendingPayment -> Paid | Cancelled; Paid -> Packed | Cancelled; Packed -> Shipped | Cancelled; Shipped -> Delivered (Shipped -> Shipped only to change the tracking code); Delivered and Cancelled are final. Cancelling gives the stock of every line back to its book in the same transaction (the stock was taken at order time) — so a cancelled unpaid order frees its books (BACKLOG 20 still open for an automatic timeout). Nothing can be cancelled once shipped (returns = a business process, task 26). Tracking code is optional text (max 50), set when shipping, correctable while Shipped. The rules live ONLY in `dbo.Orders_SetStatus` (it refuses other moves, locks the row with UPDLOCK against two admins at once); the admin UI only decides which buttons to show. "Paid" is set by hand in the admin until a payment gateway exists (phase 4).
- 2026-10-21: Orders (scripts 0015-0016). `Orders.Status` holds English codes (`PendingPayment`, `Paid`, `Packed`, `Shipped`, `Delivered`, `Cancelled`, CHECK constraint); the UI shows Persian text. `OrderLines` copy Title, Image and UnitPrice at purchase time; the recipient (name, mobile, address, postal code) is copied into the order too, so a later address edit changes nothing. `dbo.Orders_Place` takes the lines as JSON, decreases stock with ONE conditional `UPDATE ... WHERE Stock >= Quantity` and compares `@@ROWCOUNT` with the line count (race-safe: no negative stock, no explicit locks); on a problem it rolls back and answers `OrderId = 0` + `Problem` code, the controller turns it into a Persian message. Prices always come from the database, never from the browser. Shipping cost = 0 until phase 4. Unpaid orders keep their stock taken until the release rule (task 20) exists. Cart stays in the UI localStorage for now (server cart = task 15, later). Chosen with her ("do it as you suggested").
- 2026-10-19: Admin is a SEPARATE backend + UI in two repos (`TheMorisakiBookshop.admin.api`, `TheMorisakiBookshop.admin.ui`) — her request; the first version of the admin code was written inside the shop repos and moved out the same day. The shop API has no write endpoints for the catalog any more. Both APIs use the same database; THIS repo stays the only owner of `Database/Migrations/` (the admin API repo has no SQL scripts, so numbers and run order cannot drift). Admin login is separate (email + password, Admin role, own `Jwt:Key`/issuer/audience) — see the admin API DECISIONS.
- 2026-10-19: Books are hidden, not deleted: `Books.IsActive BIT` (script 0013), every shop procedure returns active books only (`Books_Search` / `Books_GetById` also take `@IncludeInactive`, used by the admin API). `Books_Delete` is dropped — future orders must keep pointing at their book. Her choice.
- 2026-10-19: Uploaded cover / author images are written by the admin API into a folder (`Uploads:RootPath`, default `../uploads`, next to the repos); the shop API only SERVES that folder at `/uploads` (`Program.cs`, `UseStaticFiles`), so BOTH `appsettings.json` must point to the same folder. The DB stores the relative path `/uploads/covers/<guid>.jpg` (domain change breaks nothing; the shop UI pipe `apiImage` adds the API origin). Production: shared persistent volume + backups (task 25).
- 2026-10-13: `Users.Name NVARCHAR(100) NULL` (script 0012): `Register` requires it (2-100 chars), `POST Auth/UpdateProfile { name }` (needs token) changes it, `UserOutputModel.Name` carries it to the UI. Only the name for now — birthdate/avatar stay in the UI profile (BACKLOG task 13 moves the rest). Her request: greet "<name> عزیز خوش آمدید" and show the name in the menu.
- 2026-10-13: "Remember me": `RememberMe` bool on `VerifyOtp`, `LoginWithPassword`, `Register`; true = token lifetime `Jwt:RememberMeDays` (30, in `appsettings.json`) instead of `Jwt:ExpiresMinutes` (60). A long-lived access token cannot be revoked before it expires (no refresh tokens / logout-everywhere yet) — accepted for now, revisit in the security pass (task 25). Her request.

- 2026-10-13: `Sms:ShowCodeInResponse` (true only in `appsettings.Development.json`) puts the OTP in the `message` of `Auth/RequestOtp` — her request, she could not find the code in the log. Program.cs refuses to start with it on outside Development. Remove it when a real SMS provider exists.
- 2026-10-13: Login = mobile + OTP (creates the account) AND email + password as a second method that a logged-in user adds with `Auth/SetCredentials`. No password-only sign-up: the mobile is always verified first, so every account has a verified phone. Password reset = fresh SMS code (`ResetPassword`) — this replaces the unverified UI mock reset. Chosen by Claude (she said "whatever you say").
- 2026-10-13: OTP rules (in SQL `0011`): 6 digits, valid 2 min, 1 code/min and 5/hour per mobile, 5 wrong tries lock the code, a used code cannot be reused. Codes stored as SHA-256 of `mobile:code` only. SMS = mock (`Security/SmsSender.cs` logs the code) — she has no provider yet.
- 2026-10-13: Passwords hashed with PBKDF2-SHA256 (100000 iterations, random salt, `Rfc2898DeriveBytes`, built into .NET — no extra package); stored as `iterations.salt.hash`.
- 2026-10-13: JWT (HS256, 60 min, claims user id + role). Key only from config `Jwt:Key` (throwaway value in `appsettings.Development.json`; production = env var `Jwt__Key`; the app refuses to start without ≥32 chars). 401/403 answer the envelope. Roles `Customer` / `Admin`; admin is promoted by hand with `dbo.Users_SetRole`. Small classes in `Security/` (not a service layer): they hold real logic that is not SQL.

- 2026-10-07: Order placement and stock decrease happen in one stored procedure inside a transaction; order lines store the price at purchase time — prevents wrong stock counts and changed old orders (her past pain with other shops).
- 2026-10-07: Login = mobile + OTP first, email + password as optional second method later (same JWT afterwards) — OTP is the common way in Iran and avoids storing passwords; two methods = more code, so the second one waits until the first works.
- 2026-10-07: Project goal: real online bookshop for real sales, single seller (no marketplace), Iranian market (Persian RTL, Iranian payment gateway, local shipping). Reason: owner had bad experiences buying books online (late delivery, wrong count, damaged books, untrusted shipping/payment).
- 2026-10-04: Every endpoint returns the `CustomActionResult` / `CustomActionResult<T>` envelope `{ isSuccess, data, message, errors }`, always HTTP 200 for business outcomes (not found = `isSuccess: false`), 400/500 only from the framework with the same envelope — the Angular `ApiHelperService` / `ApiResponse<T>` (skill angular-stack in the UI repo) depends on this shape. No ActionExecuter; controllers build the envelope.
- 2026-10-04: Basic rules taken from the helper's own .NET skill (no layering/architecture from it): `RequestModel` / `OutputModel` / `Model` suffixes, `CancellationToken cancellationToken` on every async method (Dapper via `CommandDefinition`), `List<T>` in signatures (never `IEnumerable`/arrays), empty list instead of null, classes not records — proven conventions, kept consistent with the helper's other projects.
- 2026-10-04: Database name `MorisakiBookshop`, schema `dbo` — one small app, no need for more schemas.
- 2026-10-04: Table and column names in PascalCase and identical to the C# property names (`dbo.Books.Title` ↔ `Books.Title`) — Dapper then maps columns to properties with zero mapping code.
- 2026-10-04: Stored procedure names `dbo.<Table>_<Action>` (e.g. `dbo.Books_GetById`) — all procedures of one table sit together in SSMS.
- 2026-10-04: One migrations folder `Database/Migrations/`, numbered files `NNNN_short_description.sql`, every file re-runnable; a change is always a new file, never an edit of a delivered file — she just runs new files in number order.
- 2026-10-04: Request flow = Controller → Repository → stored procedure. No service layer unless real logic appears that does not belong in SQL — fewer layers to learn.
- 2026-10-04: Repositories are concrete classes, no interface while there is only one implementation — interfaces with one implementation are ceremony. (The `I*Repository` interfaces go away when the JSON repositories are replaced.)
- 2026-10-04: C# kept deliberately plain (skill `dotnet-simple`): one class per file, no expression-bodied members, no switch expressions / pattern tricks / LINQ magic / newest-syntax features — owner is learning .NET and must read every line easily.
- 2026-10-04: Data access only Dapper + stored procedures — owner's choice, to learn SQL Server properly.
